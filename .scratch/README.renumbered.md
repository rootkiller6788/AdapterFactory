## 二、核心命题

**这个项目和 FineTuneFactory 不应该重复。**

```
FineTuneFactory 是：
Dataset → Train → Adapter

AdapterFactory 则是：
Adapter → Registry → Compose → Merge → Evaluate → Deploy
```

它研究的是 **Adapter 生命周期**——Adapter 产出之后的登记、版本、能力标注、组合、冲突检测与部署，而不是再训练一遍。

## 五、最值得做的是 Adapter Graph

```
                 Base Llama
                    │
         ┌──────────┼──────────┐
         ▼          ▼          ▼
      Coding      Math       Chinese
         │          │          │
         └────┬─────┘          │
              ▼                │
        Coding+Math            │
              └────────┬───────┘
                       ▼
                Final Adapter
```

甚至定义：

```
A* = Compose(A_1, A_2, ..., A_n)
```

然后评估：

| 指标 | 含义 |
| --- | --- |
| Capability Gain | 组合后相对单 Adapter 的能力增量 |
| Interference | Adapter 之间的相互干扰（能力此消彼长） |
| Parameter Cost | 组合后的参数 / 显存开销 |
| Latency | 推理时延变化 |
| Merge Error | Merge 引入的数值误差与能力损失 |

**核心问题**：多个 Adapter 叠加时，收益是相加、相消还是互相破坏？Adapter Graph 就是回答这个问题的地图。

## 六、阶段性落地计划

- **M0｜Registry 骨架**：定义 Adapter Record（版本、基座、能力标签、指标）schema，跑通注册与检索（非自动）。
- **M1｜Compose / Merge**：实现 Stack / Merge / Route 三种组合方式，产出可加载的组合 Adapter。
- **M2｜冲突检测与评估**：接入 Capability Gain / Interference / Merge Error 度量，做组合搜索。
- **M3｜Adapter Graph 与发布**：构建 Adapter Graph，输出组合推荐与可视化报告。

## 七、验收标准

能端到端完成「AdapterFactory」，并在其「核心」（Adapter 训练、组合、Merge、管理）上给出可复现的量化结果：

- 能对 n 个 Adapter 给出可复现的组合矩阵（Capability Gain vs Interference）
- Adapter Graph 能明确指出哪些组合会互相干扰

# 附录 A｜从设计稿到可运行的脚手架

上面那一部分是**设计稿，一字未改**；下面三个附录是它落地之后的记录。
落地的一句话题目就是第二节那句话的可执行形式：

> **本项目不训练。** 它把「Adapter 产出之后发生了什么」做成一件可以测量的东西。

## A.1 形状：设计空间是「组合空间」

用工作区判定形状的那句判据「**候选是谁挑的**」：候选是把 Adapter 子集**枚举展开**
出来的，不是搜出来的 ⇒ 扇出-收拢型。但它与前两种形态的区别在于，设计空间不是
「算法 × 规模」，也不是「某个 IR 字段的取值」，而是**Adapter 集合上的子集格**：

```
8 个冻结的 Adapter ──→ 全部 size 1..3 子集（8 + 28 + 56 = 92）
                    × 3 种组合方法（stack / merge / route）
                    = 276 个组合
                          │
                          ▼
                    实测 4 个能力 × 48 条探针
                          │
              ┌───────────┼────────────┐
              ▼           ▼            ▼
          组合矩阵     冲突矩阵     Adapter Graph
```

**这个形状独有的两件事**（别处没有的）：

1. **子集格就是血缘图。** `combo:<cid>` 节点的父节点**恰好**是它的成员 Adapter ——
   于是「谁和谁组合过」看一张图就知道，不必翻报告。Adapter Graph 不是独立产物，
   它就是 lineage DAG 的一个子图。
2. **两条独立路径必须对质。** 路径 A（**参数空间**）从 delta 张量本身算
   `cos(Δᵢ,Δⱼ)` 与符号一致率，**预测**冲突；路径 B（**能力空间**）实测
   `Interference(i,j)`。两者同向，「冲突」这个说法才有来源；**对不上就是本项目
   最有信息量的输出**——实测上确实对不上（附录 B.4），于是报告把它当结论写，
   而不是当噪声藏起来。

## A.2 架构墙：一句文档里的话，怎么变成一件能被检查的事

第二节说「不重复 FineTuneFactory 的 `Dataset → Train → Adapter`」。这句话必须是
**可执行的**，否则它只是礼貌：

| 装置 | 在哪 | 它挡住什么 |
| --- | --- | --- |
| 14 个模块的白名单 | `audit.PIPELINE_MODULES` | 流水线模块里出现训练入口调用 / `backward` / `produce` 导入 ⇒ 每次 `run` 报违规 |
| 精确一条导入边 | `audit.producer_contained` | `produce` 必须**恰好**被 `cli._cmd_produce` 一个函数导入（控制点唯一） |
| `import` 图而非文本 | `audit.no_training_in_pipeline` | 用 `ast` 看调用、用 `tokenize` 看标识符 token。**不是文本扫描**——文本扫描会扫到自己的文档字符串（复用坑 96） |
| 结果进门槛 | `result.counters["checks"]` → `acceptance` | 墙不是一条建议：它绿了 `run` 才肯写 `out/` |

诚实的边界（写在 `audit.py` 里，不是藏着的）：`tokenize` 看得见**用作值的裸名字**
`backward`，但看不见 `"back" + "ward"` 这种两个字符串字面量拼出来的名字。
逐字符的绕法挡不住；挡得住的是「顺手写一行训练代码」。

## 附录 B｜设计期望 vs 实测

按工作区约定，附录 B 要有一张「设计期望 vs 实测」表，**并且允许期望被推翻**。
本项目八条期望里，**五条成立、一条被收窄、两条被推翻** —— 被推翻的那两条
（B.4 的两路对质、B.6 的「冲突是少数现象」）是这份文档里最值钱的部分：
它们是**这次运行独有的结论**，不是设计稿里能推导出来的东西。

### B.0 一张表

| # | 设计稿里的期望 | 实测 | 判定 |
| --- | --- | --- | --- |
| 1 | 8 个 Adapter 各自学会自己那件事（增益 > heuristic） | 8/8 通过；最紧的是 `sort-qv` **+0.1246** | ✅ 成立 |
| 2 | 同能力的两个变体应当**次可加** | 最差的一对 `sort-all+sort-qv` 次可加量 **+1.2552** | ✅ 成立 |
| 3 | 「合并权重」与「逐个施加」数值上恒等 | 184 条权重空间组合，最大误差 **5.415e-14** ≤ 1e-12 | ✅ 成立 |
| 4 | 基座在四个能力上「什么都不学」 | 四个全部落在 `[chance−0.05, heuristic+0.05]` | ✅ 成立（口径改过一次，见 B.1） |
| 5 | **参数空间（cos / 符号一致率）能预测冲突** | 六个预测器 \|ρ\| ≤ 0.26，同向率 **8/28 = 0.286** | ❌ **推翻** |
| 6 | 冲突是**少数**现象，图上只有稀疏的干扰边 | **28/28 对全部有害**，最轻 +0.5234、最重 +0.9896 | ❌ **推翻** |
| 7 | `merge` 的「稀释」是它区别于 `stack` 的地方 | `merge_loss` 几乎为 0（均值 **+0.0009**），`stack` 一样被摊薄 | 🟡 收窄 |
| 8 | `route` 靠「保持分离」更好，代价是多花算力 | size≥2 时最好（−0.0142 vs −0.0258），MACs 是基座的 1.17–1.86 倍 | ✅ 成立 |

第 5、6 条合起来是同一个故事的两面，见 B.4 与 B.6。第 7 条收窄的意思是：
**「摊薄」确实发生了**（size≥2 时成员自己的能力从 +0.7428 掉到 −0.02 附近），
但它**不是 `merge` 特有的** —— `stack` 掉得一样多。设计稿把「稀释」记在
`merge` 头上，实测说明真正的机制在两者**共有**的那一步（把 Δ 加进同一个挂点）。

### B.1 两条基线：`chance` 与 `heuristic`

基座 `tiny`（2 层 / d_model 24 / 4 头 / d_ff 48 / RoPE）在四个能力上的
逐 token 准确率（n_eval=48，即分辨率 1/48 = 0.0208）：

| 能力 | `chance` | `majority` | `copy` | **`heuristic`** = max(多数, 照抄) |
| --- | --- | --- | --- | --- |
| upper | 0.1250 | 0.1250 | 0.0000 | **0.1250** |
| shift | 0.1250 | 0.1458 | 0.0000 | **0.1458** |
| reverse | 0.1250 | 0.1615 | 0.1458 | **0.1615** |
| sort | 0.1250 | 0.2500 | **0.3021** | **0.3021** |

两件必须写下来的事：

- **`chance` 是 `1/|payload_chars|` = 1/8 = 0.1250，不是 `1/vocab`**（1/26 = 0.0385）。
  这两者在「随机猜」这个词下都「看起来合理」，差 3.25 倍。用错的那个会让
  每条增益都虚高，而**没有任何一处会报错**（复用坑 47）。
- **验收盯的是更强的 `heuristic`，不是 `chance`。** 能看输入但不学习的策略
  至少能照抄，所以真正的「学会了」的下界是 max(多数字, 照抄)。
  `sort` 上这两支分叉得最远（照抄 0.3021 > 多数 0.2500）—— 而在
  FineTuneFactory 里，`sort` 恰好也是**「正好等于乱猜」被读成「高于乱猜」**的那一支
  （坑 106）。同一个能力踩了两次，所以这里把三支分开印。

### B.2 `lr` 不是瓶颈

标定从 `lr` 开始，因为 FineTuneFactory 的实测（README B.2）说它的 LoRA
在 `lr=0.03` 时**恰好等于乱猜**。本项目把 `lr` 提高一倍（5e-3 → 1e-2，
步数 800）看能不能救回两件难的任务：

| 配方 | `reverse-qv` 差 | `sort-qv` 差 |
| --- | --- | --- |
| rank4 · **lr 5e-3** · **400 步** | −0.0313 ✗ | −0.0990 ✗ |
| rank4 · lr 1e-2 · 800 步 | +0.1718 ✓ | +0.1146 ✓ |

两件都过了 —— 但**不是单调改善**：在 rank4 下把 lr 降到 5e-3 而把步数提到
1200，`reverse-qv` 反而更好（+0.3906），`sort-qv` 更差（+0.0781）。
所以 lr 与步数是一对可以互相替代的旋钮，`lr` 单独不是瓶颈。
与 FineTuneFactory 那个「lr=0.03 恰好乱猜」的结论并不冲突：那是在**全量/四策略
对比**的量级上测的，这里的 delta 挂在一个 d_model=24 的基座上，参数量差了若干量级。

### B.3 `rank` 才是瓶颈（标定表）

S0 的硬门槛是「8 个 Adapter 都超过 `heuristic` + 0.10」。第一次真实运行
**卡在这里**：`reverse-qv` 差 −0.031、`sort-qv` 差 −0.099，两条没过。
下面这张表是**复跑出来的**（只训这两个 qv 变体，训到临时目录，
`gap = acc − 基座 − heuristic`）：

| 配方 | `reverse-qv` acc | 差 | `sort-qv` acc | 差 |
| --- | --- | --- | --- | --- |
| rank4 · lr5e-3 · **400 步**（原配置） | 0.2344 | −0.0313 ✗ | 0.3854 | −0.0990 ✗ |
| rank4 · lr5e-3 · **1200 步** | 0.6562 | +0.3906 ✓ | 0.5625 | +0.0781 ✗ |
| rank4 · **lr1e-2** · 800 步 | 0.4375 | +0.1718 ✓ | 0.5990 | +0.1146 ✓ |
| rank4 · lr5e-3 · 400 步 · **wd 0.01** | 0.2396 | −0.0261 ✗ | 0.3802 | −0.1042 ✗ |
| **rank8** · lr5e-3 · 800 步（**采用**） | **0.6771** | **+0.4114** ✓ | **0.6094** | **+0.1250** ✓ |

怎么读这张表：

- **加正则没用**（第 4 行与第 1 行几乎一样）⇒ 不是过拟合，是没学会。
- **加步数只救回一半**：rank4 下 400→1200 步把 `reverse` 救回来了（−0.0313 →
  +0.3906）但 `sort` 仍然差（+0.0781）⇒ **不是「训练时间不够」，是「容量不够」**。
  这两件事在损失曲线上的表现是同一件事（都是损失降不下去），只有把 rank 单独
  动一次才能把它们分开 —— 这是这个标定里唯一真正需要实验的地方。
- **提 lr 也过得去**（第 3 行）：所以 rank8 不是唯一解。选它的理由是**裕度**：
  rank8 下最紧的一条是 +0.1250、`reverse` 是全部五行里最好的 +0.4114；
  lr1e-2 那条虽然都过，但 `reverse` 只有 +0.1718。**一个「也过得去」的解
  和一个「裕度大一倍」的解，在门槛旁边的表现是不一样的** —— 门槛是 0.10，
  前者离它只有 +0.0146（`sort`）。
- `alpha = alpha_mult × rank` 恒为 `2 × rank`（rank4 → alpha 8、rank8 → alpha 16），
  所以第 5 行相对第 1 行改的是**容量**（每个模块多做多少参数的更新），
  而 LoRA 的**有效缩放**（`scale = alpha/rank`）**保持恒等于 2 不变** ——
  把倍数放进配置而不是写死，改 rank 时才真的是单变量。

复跑的第五行与生产运行的实测**逐位相同**（`reverse-qv` 0.6771、`sort-qv` 0.6094
对 `produce` 打印的 0.677 / 0.609）⇒ 训练配方是可复现的。

### B.4 两路对质：**路径 A 被推翻**

设计稿说「两条独立路径必须对质」：路径 A 从 delta 张量本身预测冲突
（`cos(Δᵢ,Δⱼ)`、符号一致率），路径 B 实测干扰。28 对全部可预测，结果是：

| 预测器 | Pearson ρ | Spearman ρ |
| --- | --- | --- |
| `cos` | −0.081 | −0.027 |
| `sign_rate` | **−0.256** | −0.144 |
| `expansion` | −0.196 | −0.204 |
| `overlap_ab` | −0.219 | −0.131 |
| `overlap_ba` | +0.029 | +0.283 |
| `norm_ratio` | +0.178 | +0.111 |

**六个预测器没有一个能用**：\|ρ\| 全部 ≤ 0.26，而绝对值最大的两个
（`sign_rate` −0.256、`overlap_ab` −0.219）**是负的** —— 也就是说，
「两个 delta 越对齐、共同挂点越多 ⇒ 越容易冲突」这个直觉，在数据里的
微弱倾向**恰好相反**。同向率 8/28 = **0.286**（门槛 0.50）⇒ 路径 A 不成立。

S0.5 的方法探针在另一个配置上（rank4、n_eval 64）独立得到同一个结论：
同向率 1/6 = 0.167。**两个配置、两套探针集，同一个结论。**

剩下的机制假设是**幅度，不是方向**。量级表（**生产用的 rank8 zoo**，
`data/adapters/` 里那 8 份，逐个按挂点算）：

| delta | ‖Δ‖ | ‖W_挂点‖ | 比值 | 挂几个模块 |
| --- | --- | --- | --- | --- |
| `shift-qv` | 96.79 | 0.797 | **121.5** | 2 |
| `sort-qv` | 65.71 | 0.797 | **82.5** | 2 |
| `upper-qv` | 56.99 | 0.797 | 71.5 | 2 |
| `reverse-qv` | 52.95 | 0.797 | 66.5 | 2 |
| `reverse-all` | 25.00 | 1.681 | 14.9 | 7 |
| `upper-all` | 20.55 | 1.681 | 12.2 | 7 |
| `sort-all` | 19.19 | 1.681 | 11.4 | 7 |
| `shift-all` | 18.52 | 1.681 | 11.0 | 7 |

**一个 delta 的范数是它挂点权重的 11–121 倍。** 注意 qv 与 all 分成两簇
（66–121 vs 11–15）：这不是巧合 —— 挂 2 个模块的变体把同样的容量挤进更少的
参数里，单个 delta 就更长。这也解释了为什么 `qv` 变体更需要容量
（B.3 的标定打的就是它们）。

S0.5 的方法探针在 rank4 上得到同一件事（比值 6.9–95.7），量级一致、
数值按容量缩放 —— 两个 rank、两套探针集，同一个机制。

一个 delta 的范数是它挂点权重的 **7–96 倍**。把两个这样的东西加起来，
不会「方向互相抵消」，只会**把挂点推得比训练时见过的远得多** ——
过冲。这个解释给出一条可证伪的预测（`merge` 的系数 1/k 应当把这一对救回来），
而这条预测**在报告里被检查了**（见 B.6 的 `merge_loss`）。

### B.5 冻结 zoo 的实测（8 个 Adapter，rank 8，800 步）

| Adapter | 自己能力 acc | 差 = acc − 基座 − heuristic（门槛 0.10） | upper | shift | reverse | sort |
| --- | --- | --- | --- | --- | --- | --- |
| `upper-qv` | 0.870 | +0.6252 | **0.870** | 0.000 | 0.000 | 0.000 |
| `upper-all` | 1.000 | +0.7552 | **1.000** | 0.000 | 0.000 | 0.000 |
| `shift-qv` | 0.922 | +0.6824 | 0.010 | **0.922** | 0.057 | 0.104 |
| `shift-all` | 1.000 | +0.7604 | 0.000 | **1.000** | 0.062 | 0.109 |
| `reverse-qv` | 0.677 | +0.4113 | 0.005 | 0.010 | **0.677** | 0.219 |
| `reverse-all` | 0.995 | +0.7293 | 0.000 | 0.109 | **0.995** | 0.271 |
| `sort-qv` | 0.609 | +0.1246 | 0.010 | 0.026 | 0.167 | **0.609** |

两点值得单独说：

- **矩阵对角线之外几乎全是 0.000–0.271。** 单 Adapter 之间**没有串扰**：

  这件事让 B.6 那个结论变干净了 —— 后面测到的干扰**全部来自「组合」这个动作
  本身**，不是来自训练。
- **`all` 变体普遍强于 `qv` 变体**，幅度最大的是 `sort`（0.870 vs 0.609）——
  与 B.3 那张标定表同向（`sort` 是两件难任务里更难的一件，需要的容量更大，
  挂 7 个模块比挂 2 个更够用）。

### B.6 干扰的实测分布：**28/28 全部有害**

28 对 Adapter 两两之间的对称化干扰（`interference(i,j)`，判有害的门槛取
1/n_eval = 0.0208 —— 低于这个量级时符号由浮点噪声决定）：

```
+0.5234  reverse-qv ~ sort-qv     ← 最轻
+0.5859  shift-qv   ~ sort-qv
+0.6276  sort-qv    ~ upper-qv
   ...（中略，逐对明细见 out/conflict.json）
+0.9323  shift-all  ~ upper-all
+0.9896  reverse-all ~ upper-all  ← 最重
```

**最轻的一对是 +0.5234，比门槛高 25 倍。** 所以「全部有害」不是一个
卡在门槛上的结论，是分布整体远远在正侧 —— 期望「只有少数几对冲突」被推翻。

这一点也在成员自己的能力上看得出来（同一批组合，按方法平均）：

| 方法 | size-1 成员能力增益 | size-2 | size-3 | MACs |
| --- | --- | --- | --- | --- |
| `stack` | +0.7428 | **−0.0258** | −0.0667 | 186368（= 基座） |
| `merge` | +0.7428 | **−0.0219** | −0.0661 | 186368（= 基座） |
| `route` | +0.7428 | **−0.0142** | −0.0534 | 218816–347360（1.17–1.86×） |

单干时能力是 **+0.7428**，任意两个组合起来就掉到 **0 附近**（甚至是负的，
意味着比基座还差）。三条方法都这样，`route` 只是稍微不那么差。

**这里正好检验了 B.4 那条可证伪的预测。** 如果干扰的主因是「幅度过冲」，
那么把系数除 k（`merge`）应当能把它救回来；实测 `merge_loss` 的
均值是 **+0.0009**（92 条，范围 −0.043..+0.034）—— **没救回来**。
所以更准确的表述是：**除以 k 不足以抵消过冲**。注意 `merge` 除的是 k
而**不是**范数：它把 `Δ₁+Δ₂` 除以 2，而两个 delta 是**近似正交**的
（28 对的 `cos` 中位数 **+0.028**、\|cos\| 中位数 0.039 —— 见上表，
这也是六个预测器全部失效的直接原因），于是 ‖Δ₁+Δ₂‖ ≈ √2·‖Δ‖，
除 2 之后还剩 **0.7 倍** —— 从 11–121 倍过冲变成 8–86 倍过冲，量级没变。
设计稿把「稀释」记在 `merge` 头上（第 7 条期望），实测说明 `merge`
与 `stack` 在这里没有实质区别。

### B.7 这些结论在哪失效

诚实划界，免得被当成普适规律：

- **「28/28 全部有害」是这台标本的性质，不是 Adapter 组合的普适定律。**
  它的直接原因是 B.4 那张量级表：基座只有 d_model=24，LoRA 的 delta 范数是
  挂点权重的 7–96 倍。在一个 delta 很小的配置上，干扰很可能不是全正。
  要测「组合什么时候有用」，得换一台 delta 相对挂点更小的标本。
- **`route` 的「稍微不那么差」没有统计上的强度。** 三个数分别是
  −0.0142 / −0.0258 / −0.0219，差在分辨率（1/48 = 0.0208）上下 ——
  只能读成「分离不比相加更差」，**不能**读成「分离明显更好」。
- 所有数字都是**一台基座、一个种子（20260930）、一个探针集（n_eval=48）**上的。
  换种子会动小数点后两位 ——
  门槛旁边的那两条（`sort-qv` +0.1246 与 +0.1000 之间只有 0.0246）会最先翻。

### C.1 架构墙（126–129）

**126｜墙第一版禁的是名词，不是动作。**
第一版查标识符 `train`，实测扫出 15 处：`config["train"]`、`ZooRecord.train`、
`AdapterRecord(train=...)`——**全是名词**，没有一处是训练动作。于是要么改名迁就检查
（`train` 是个好名字，凭什么改），要么加白名单——而白名单会在下一次真的写出
`train_adapter(...)` 时把它一起放过。**修法**：墙改查**动作**（训练入口被调用、
`backward` 被调用、`produce` 被导入）。出处 `audit.py` 模块 docstring。

**127｜把不做梯度更新的函数当成训练入口报违规。**
`build_train_set` 与 `batch_order` 曾经在 `FORBIDDEN_CALLS` 里。它们名字里有 `train`，
但都不更新权重。后果是流水线要么算不出基线，要么为了迁就检查去找一个**语义不同**的
替代实现。**修法**：移进 `DATA_SIDE_CALLS`——**照报，但不否决**。「报」与「否决」是
两件事，混成一件就会逼出上面那种荒唐选择。

**128｜配置里存在过两个「可以关掉」的开关，而文档说它不存在。**
`require_no_training_in_pipeline` 与 `require_grid_complete` 默认 `True`，于是
「能关掉」这件事**从不显形**，直到有人去读代码。docstring 与配置注释都写着
「结构性四项没有开关」，代码里却有——**文档在陈述一件代码没做的事**。
更糟的是那条判据不只是文案：它意味着一份把结构性核对关掉的配置能通过全部检查。
**修法**：删掉两个键；`required` 写死 `True`，**不读配置**。并且留了一条**惰性**的
防线——`test_audit_wall.py` 现在故意把这两个开关塞回配置里，断言检查根本不看它们。

**129｜「基座该贴机会水平」写成对称容差，于是第一次真实运行就红了。**
原来是 `|base − chance| ≤ slack`。`sort` 上基座实测 0.1823、`chance` 0.125，
偏离 +0.0573 > 0.05 ⇒ 判越界。**而 0.1823 是这道题的性质**：基座能看见输入，
「什么都不学」时是**照抄**；`sort` 的输出是输入的排列，平均约 1.4/8 个位置是
不动点，照抄就能拿到 ~0.175。对称的那一半是错的。

这里最值得记的不是公式，是**修的是检查的口径，不是门槛的数值**。把 `slack` 从
0.05 调到 0.10 同样能变绿，而那等于用调参把一条说真话的检查关掉。
**修法**：两侧不对称——下界 `chance − slack`（基座低于机会水平会**抬高每一个
gain**，那是危险的方向），上界 `heuristic + slack`（基座超过最强的平凡预测器时，
「gain 衡量的是 Adapter 的贡献」这句话就不再成立）。顺带改名 `base_at_chance`
→ `base_is_null`：旧名字陈述了一件检查没做的事。

### C.2 口径：两处各写一遍（130–132）

**130｜`exclude` 不在缓存键里。**
`build_train_set(..., exclude=评测 payload)` 与不带 `exclude` 的调用**撞同一个
缓存键**。哪个先跑，后跑的那个就静默地拿回**含评测样本**的那一份。整个过程
一句警告都没有，直到 `produce_zoo` 里那句显式的重叠检查把它抓住——而那是一个
**运气**：两处调用的先后顺序决定一切。**修法**：凡是能改变输出的参数，一律进键。

**131｜「训练集与评测集不相交」曾经有两个实现。**
排除逻辑写在 `produce.produce_zoo` 里，而 `pipeline.prepare` 另建了一份**不排除**的
训练集。两份都「对」——但只有一份是干净的。于是「不相交」从一条**不变量**退化成了
「取决于你问的是哪一份」。**修法**：抽成 `excluded_payloads`，两个调用方共用同一个
映射、同一个缓存键。**一个不变量如果有两个实现，它就不是不变量。**

**132｜`Adjudication.macs` 是缓存状态的函数。**
它曾经是一个字段，而且**算不对**：那个和是在逐样本的缓存命中之上累加出来的，
命中一次就少算一次。它不是「有点不准的 MACs」，它是**另一件东西**。
**修法**：删掉，MACs 只留一个来源 `macs_of`。

### C.3 图与血缘：空图会静默通过验收（133–135）

**133｜对一个 dict 取属性，安静地拿到默认值——整张图退化成两个节点。**
`build_lineage` 原来读 `getattr(result, "adapters", ())`，而三个调用点**全传 dict**。
于是图退化成 `{'base:…, 'sel:compose':…}` 两个节点、**零条边**。它不报错，看起来
只是一个稀疏的图。

**这才是要记的地方**：在这个 bug 底下，验收标准 ②「Adapter Graph 能明确指出哪些
组合会互相干扰」会**空着通过**——没有东西互相干扰，因为图上没有东西。
只写 `assert graph.n_nodes > 0` 是不够的（收拢点那一个节点就足够让它成立）。
**修法**：`_f` 两种形式都读；测试断言图的**规模量级**，不只是非空。

**134｜空图底下的第二个 bug：收拢点建晚了。**
收拢点曾经在最后才建，于是「组合 → 收拢点」那条边的终点还不存在，`add_edge`
抛 `ValueError: 边的终点不存在`。这条错误在空图存在时**永远走不到**。
**修法**：收拢点**先建**。

**135｜两个 bug 叠着，报出来的是后面那个，而根因是前面那个。**
`label=lab` 撞上 `add_node` 的第三个形参 ⇒ `TypeError`。这一行**原本就在**，
只是在 133 那个空图 bug 存在时永远走不到。修 133 的时候它才冒出来。
**教训**：修好一个 bug 之后立刻重跑——你修的那个可能一直遮着下一个。

### C.4 共享的实现：两条路径不是两份证据（136–141）

**136｜门向量一律 24 维。**
第一版把 `route` 的门向量定成 `d_model=24` 维，于是在 `down_proj` 上拿一个 24 维的
门去点一个 48 维的激活。`gate_coeffs` 抛错拦住了它（`激活维度 48 != 门向量维度 24`）。
**但真正该记的是它差点怎么溜过去**：若当初写的是 `zip` 截断，它会静默变成
「只看前 24 维的点积」——数值合理、不报错、结论错位。**修法**：`module_indims`
按模块的真实输入维。

**137｜`for i in range(1, 64)`——起点写成 1，第 0 层被静默跳过。**
它不报错、不抛异常，只是组合的效果**少算了一层**。而 `merge_into` 与 `deltas_for`
用的是**同一段**展开逻辑，于是「合并权重前向」与「逐个施加」依然逐位相同，
`merge_error` 依然是 1e-17，恒等式照样成立。

> **共享 bug 的两条路径不是互相独立的证据。**

这条比它看起来更重：本项目整个「两条路径必须对质」的可信度装置，其有效性
**完全依赖两条路径走的是不同的实现**。它们共用的每一个函数，都在削弱那句
「对质」。出处 `net.py`；`.scratch/smoke_engine.py` 里有一条专门钉它的 smoke 检查。

**138｜门向量按标签派生，不按下标。**
按**下标**派生的话，删掉第 2 个 Adapter 会让第 3 个顶上来：`route` 的全部结果
都会变，且没有任何东西会提示这件事。反过来，「按标签取」这条纪律也会被写成
「按标签取、但遍历时用 `enumerate` 的下标」——同一个错的两种长相。**修法**：
标签派生；`gate_coeffs` 与门向量的生成共用 `expand_targets`。

**139｜派生文件和源文件放在同一张清单里。**
`out/report.html` 一度和源文件一起放在 `OUT_FILES` 里。后果很具体：删掉或写坏
`report.html` 之后，**每一条只读命令都开始说「还没有产物，先跑 `run`」——包括
`visualize`**。补救手段被它要补救的条件挡住了，而唯一的出路是重跑整条 276 组合
的流水线。**修法**：拆出 `DERIVED_FILES`；「完整性」的门槛留在**写**侧，读侧只要求
源文件齐。

**140｜「训练集里排不排评测样本，无所谓」。**
看起来无所谓：基线是在训练集上算的，评测集另算。**不是的**——`majority` 是逐位置
取**训练集里的众数**，训练集里混着评测 payload 时，那条基线就偷看了评测集。
一旦偷看，所有 gain 一起偏高、差异被压扁，而**差异正是本项目唯一要测的东西**。

**141｜`merge_loss` 依赖「`plan_grid` 恰好把 `stack` 排在 `merge` 前面」这条隐式约定。**
改了方法顺序，它**静默变成 `None`**——而 `None` 在报告里渲染成「—」，
「没测到」与「本来没有」长得一模一样（复用坑 104 的同一个病）。
**修法**：两遍扫描，先收集 `stack` 的指标再算，不依赖行序。

### C.5 流水线与产物：看起来合理的错数字（142–144）

**142｜`route` 那一行拿到了一个和 `stack` 行一模一样的数。**
`merge_error` 以前是**无条件**算的，于是 `route` 行也填了一个数。而 `route` 根本
不走权重空间——它是**另一个方法的结论被复制到了这一行**。取值 ~1e-16，
看起来完全正常；`merge_identity` 一路绿（因为 stack 行确实是同一量级：
184 条里中位数 5.3e-16、最大 5.4e-14）。
后果是下游任何对 `merge_error` 求平均 / 求相关的聚合，都会**静默地多算一遍 stack**。
**修法**：`route` 上填 `None`，宁可让报告显示「—」。
`schema.py` 的模块 docstring、`cli` 的打印分支、两条测试夹具都早就写着「route 不走
权重空间」——**三处文档都对，只有代码是错的**。

**143｜沿用条件写成「文件在不在」。**
`produce` 的判断原来是 `if stem.with_suffix(".json").is_file()`。把 `zoo.rank` 从 4
改成 8 之后，8 个产物被**原样沿用**：配置、报告、`registry` 三处都写着 rank=8，
而权重全是 rank=4 训出来的。参数量、`MACs`、`rank_total` 全跟着错，
**而没有任何一处会自相矛盾**——每个数字单看都合理，只有拿来跟另一处比才不对。
而这个 bug 之所以能活下来，不是因为它错，是因为它**错得没有声音**：打印的是
`[沿用]`，一个看起来完全正常的词。

**修法**是三层的，缺一层都不够：
1. 产物的旁证里**记下被请求的那份配方**（`spec` 字段）；
2. `produce` 比对配方，不一致就重训，并**打印是哪个字段变了**；
3. `registry.load_registry` 也比对——因为「写的时候挡住」挡不住**已经写坏了的
   磁盘**，而只读路径是唯一每次都经过的地方。

这条最贵的地方在于：它同时是「配置即口径」这条纪律的**反例**。配置说了算的
前提是**产物必须真的是那份配置的产物**，而这件事以前没人核对过。

**144｜「张量成对」那道检查把键数当挂点对数用。**
它写成 `seen_hooks * 2 != len(tensors)`，而 `seen_hooks` 数的**就是键**、不是挂点
对数——于是它对**每一份形状完好的适配器**都成立，把**全部**适配器判成不相容。
症状极具迷惑性：跨基座的产物**本来也确实不相容**，所以这个 bug 藏在一堆真实的
`False` 后面。**修法**：按挂点分组，核对两个因子。出处
`registry.read_foreign` / `test_pipeline_e2e`。

### C.6 报告与文案：同一份产物渲染出两段文本（145–150）

**145｜`v or 0` 把「这个能力没测」显示成了「这个能力全错」。**
`None`（没测到）、`NaN`（无定义）、`0.0`（真的全错）是**三件事**，`or 0` 把它们
一起变成第三件。第一版正是这样。**修法**：`fmt_float` 是唯一的格式化出口。

**146｜公式里的一个管道符把 markdown 表格从中间劈开了。**
一句 `Σ C(4,k)·|方法| = 42` 写进了核对表的详情栏，markdown 于是把这行劈成两半，
渲染出来是**两张错位的表**。症状不是报错，是列错位——数字仍然对得上行、
对不上列。**修法**：转义。

**147｜`affected.items()` 的顺序活不过 JSON 往返。**
`to_dict` 用了 `sort_keys=True`，于是重读一遍之后字典键序变了。后果**不是
「数字错了」**，而是**同一份产物渲染出两段不同的文本**：`main.py report` 会说
「磁盘上的 `report.md` 与现生成的不同」——而**重跑 `run` 不会修好它**，
因为它每次都随字典序生成另一段文本。**修法**：按能力序 + 名字确定排序。

**148｜手写的项数，写了两遍，两次都错。**
报告正文写过「8 项」，而下面是 9 行（第 10 项 `artifact_roundtrip` 只在导出时
出现）——**报告正文与它下面那张表当场自相矛盾，而两处都「看着对」**。
**修法**：报告改成从清单**数出来**。然后同一个数字在 `cli.py` 的帮助文案里
又硬编码了一次（「9 项运行时核对」）——帮助文案比报告更难核对，它在一个还
没有任何产物的进程里被渲染出来，**没有清单可数**。**修法**：那里改成只说
「有哪些」，不说「有几项」，并加一条测试扫描所有帮助文案里的 `\d+ 项`。

**149｜`heuristic` 是逐 token 的，拿它跟整串全对率比。**
第一版就这样比过一次，得出「适配器打不过照抄输入」——**那是口径制造的结论，
不是实测**。两个量一个在 token 上平均、一个是整串全对，相减出来的差值没有含义。
**修法**：两种口径**永不混用**；逐 token 准确率只有一处实现（`data.mean_accuracy`），
要重写就是为了不让「评测用一套口径、基线用另一套」再发生一次。

**150｜可复现性例外表少了一项，于是相等断言随机成立。**
`counters.runtime_s` 曾经不在 `VOLATILE_PATHS` 里。后果是
`stable_view()` 的相等断言会随两次运行的时长差在 **0.05 秒**上下**随机**成立或
失败——而它本来是一条「两次运行逐位相同」的断言。**这条测试抓不住它**：
它比的是「同一份结果改了 `created_at` 之后的自己」，而那份结果的两半本来就同源。

**修法**：例外表补全，并给 `is_volatile` 加了**双向**测试——既验「每条声明的路径
都真的被实现」，也验「没声明的字段一律**不**被当成例外」。顺带修了模板匹配的一个
副产品：`runs[].wall_ms` 这个模板**不匹配它自己**（`[]` 里的下标记不是数字），
否则「例外表里的每一条都要被实现」这条断言会拿模板自证。

### C.7 测试自己：绿着绿着就不查了（151–159）

**151｜zoo 的目录定义住在 producer 里。**
`AdapterSpec` 与 `default_zoo` 是**纯描述**，一次训练都不做，但它们曾经住在
`produce.py`。后果是只读命令 `main.py task` 为了打印「zoo 规格」这张表，
必须 import 整个训练模块——于是「只读路径不加载训练代码」这句话只是**文档里的
一句话**，而不是一件能被检查的事（而 `producer_contained` 检查的正是后者）。
**修法**：搬到 `zoo.py`；producer 从此只被 `cli._cmd_produce` 一个函数够得着。

**152｜两份写下来的配置漂移，而说它们相同的那条断言只比了一节。**
`configs/default.json` 曾经比 `DEFAULTS` 多两个键（就是 128 那两个开关）——
两份配置漂移时，**真正生效的是哪一份取决于加载路径**，而这类分歧不会有任何报错。
守着「逐键相同」那条断言**一度只比 `acceptance` 这一节**，于是它在最该拦住的
地方是过宽的；那条注释里还写过一个**从来不存在的文件名** `test_config.py`。
**修法**：比整份文件（只除开 `_comment`），并在注释里写下真实的测试名。

**153｜`marked` 与 `range(response_start, ...)` 当成同一个东西。**
第一版断言两者相等，得到 `[7,8,9,10,11]` 对 `[8,9,10,11,12]`——**差 1 的错位是
这类 bug 的标准长相**。后果是**第一个回答 token 永远没有梯度**。
**修法**：分开断言，并把「第一个」这件事单独钉一条。

**154｜MACs 轴整条恒为 0——而 0 看起来只是一个「很小但合理」的值。**
`mac_ids` 取的正是**第一个评测样本**的 ids，而 `measure` 先跑、已经把那些 ids
灌进了缓存。于是 `macs_of` 次次命中，计数恒为 0。它不抛错、不违反任何检查，
只是让非支配前沿的第三个轴退化成恒等，让 `route`「多做一次乘法」失去全部证据。
**这是本项目最值钱的一条回归测试**：先灌热，再计数，并要求非零。

**155｜把 `A` 与 `B` 一起取反去测 `cos`。**
`(−B)(−A) = BA`——得到的是**同一个** delta，于是 `cos` 算出 `+1`。
而 `+1` 看起来同样「像个答案」（一个完美的冲突预测）。**修法**：只能翻**一个**因子。
出处 `test_evaluate_conflict` 的探针。

**156｜用张量名当键，而三个 Adapter 的张量名是同一套。**
第一版只用张量名当键，字典于是只剩**最后一个**适配器的值；那条断言变成
「第三个适配器没被改」——前两个改没改它根本看不见。**这类错误修一次就够了：
它安静地通过。** **修法**：键里带上适配器的身份。

**157｜`to_dot(kinds=graph.ancestors("sel:compose"))`。**
这是一句读起来**完全正确**的代码（它想问「收拢点及其全部祖先」），而 `kinds=`
要的是一个**种类的集合**，于是传入的节点 id 一个都对不上：输出 `digraph
lineage {}`——**一份合法的 DOT，画出来是白纸**。语法检查会放过它，只有「渲染出来
有几条边」能抓住它。**修法**：`kinds=` 收节点集合的语义单独测一条。

**158｜注入测试注入了一个会被跳过的串。**
那条测试给图表注入一段标记再断言它出现。曾经注入的是**能力名**，而能力名在某些
图表里会因为「该能力没有指标」被跳过——于是注入的那个串一个字符都不出现，
断言退化成「不包含」的恒真式：**一条永远绿的测试，看起来在验一件事。**
**修法**：注入一个不可能被跳过的串。

**159｜夹具依赖错了东西。**
`tiny_root` 只保证**目录存在**，写出 `out/` 的是 `result`。带了
`out_copy`（拷贝 `out/`）而**没有请求 `result`** 的测试，在全量运行时是绿的
（那时别的测试恰好已经把 `out/` 建出来了），在**单独跑这一条时炸**。
同一类错误在本项目里出现过两次（`test_pipeline_e2e` 的 12 个产物、
`test_report_cli` 的 `out_copy`）。**修法**：夹具依赖**写出它的那个东西**，
并把这个理由写在夹具的 docstring 里——否则下一个人会「顺手」把依赖改回去。

### C.8 一句话版本

上面 34 条里，**30 条的症状是「一切正常」**。另外四条（126、127、129、136）
反而**是响的**——它们抛了异常或当场判红。把这四条留在名单里，是因为它们
各自都差点以安静的方式溜过去：126 与 127 是**规则**写错了（会把好东西判成坏的，
于是下一次真的违规时白名单会放过它）；129 若不是在第一次真实运行时就撞上，
把容差从 0.05 调到 0.10 同样能让它变绿——**那次红是运气**；136 若不是
`gate_coeffs` 抛错，写成 `zip` 截断就是静默的。

真正值得记的不是「哪里写错了」，而是这个形状：

> **错误的数字看起来和正确的数字一模一样。**
> `0`（MACs 恒零）、`None`（route 的 merge_error）、`1e-17`（少算一层的恒等式）、
> `+0.1823`（照抄输入的基座）、`rank=8`（一套 rank=4 的权重）、
> `+1.0`（把两个因子一起取反得到的 `cos`）——
> 它们都不是「看起来坏了」，它们是「看起来没坏」。

对付这个形状，本项目用的办法只有三个，没有一个依赖小心：

1. **让同一件事实有两个来源，然后强迫它们对质**（参数空间 vs 能力空间、
   内存 vs 磁盘、配置 vs 产物、帮助文案 vs 清单）。对质失败是**输出**，不是噪声。
   附录 B.4 就是这条办法产出的**反面结论**：两条路径对不上，于是「冲突源于
   参数空间的对齐」这个假设被证伪了。
2. **数出来的东西不写死**（项数、网格大小、偏移量、条数）。
3. **每一道检查都要有一条「反向」的测试**：不只验「对的能过」，还验
   「错的那种必须被点出来」——否则你验的是尺子，不是被测物。
   `test_rng_schema` 里那条「例外表双向核对」、`test_compose` 里那条
   「改了配方必须重训」、`test_evaluate_conflict` 里那条「先灌热再计数」，
   都是这个形状。

### C.9 悬空引用

附录 A/B 里多处被代码注释引用（`config.py` 的标定表、`evaluate.py` 与
`schema.py` 的口径记录）。**这些引用在本附录写下之前是悬空的**——它所指向的
附录当时并不存在。这不是笔误，是「先写引用、后写内容」的顺序留下的：
代码那边注释写得越具体，越容易把读者引到一个还不存在的地方。
补上，而不是删掉引用，因为它们记的**确实是**那两件事。
